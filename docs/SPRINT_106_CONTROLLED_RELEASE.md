# Controlled release channel — prepared only

Workflow s106-controlled-release.yml is manual, main-only, exact SHA + official push/main QG 4/4, independent rules/functions confirmations, fixed project and five-function allowlist. It rechecks remote main before authentication, before dry-run, and before publication. Installations preserve lockfiles. Dry-run requires the functions stage and is potentially mutating, never a read-only audit. No dispatch is authorized by this document.

Functions stage is hard blocked by FUNCTIONS_RELEASE_READY=false before authentication. Resolve WhatsApp consumer dependencies and mixed-revision rollout in a separately reviewed change before unlocking it. A confirmation input cannot override the lock. The five candidates are createEmployee, updateEmployee, enableEmployee, disableEmployee and askBusinessAI. No absent endpoint, public Function, admin endpoint, or whatsapp export is included. Package discovery still imports modules/Secret declarations; never assume --only prevents API discovery side effects. Future authorization must explicitly address required API changes; stop on unapproved IAM/Secret/configuration changes.

Inputs: stage=rules + confirmacao=PUBLICAR_RULES, or stage=functions + confirmacao=PUBLICAR_FUNCTIONS; sha is the full current main SHA. The current hard block makes the second combination intentionally unusable. Rules-only authorization must not imply Functions authorization. Scope is chosen from literals, not a user-provided list.

Immediately before each Firebase CLI invocation, the shell independently revalidates the stage, its exact confirmation, full SHA and checkout, fixed project, five-function allowlist, release flag and effective TARGET_SCOPE. It derives the expected scope from closed literals and requires byte-for-byte equality, without trimming or normalization. The validated TARGET_SCOPE is made readonly and is the same variable passed to --only. Missing/invalid flags or a corrupted/empty/expanded target stop before the CLI; a Rules stage cannot become a Functions, Storage or indexes operation. The dry-run block additionally requires the Functions stage, even when tested independently of the Actions if condition. FUNCTIONS_RELEASE_READY remains false; no Functions dry-run or publication is enabled by this hardening. Rules remains a separately authorized manual path, not a globally disabled stage.

Concurrency group matches existing production Functions channels. Legacy Beta/Rules workflows use different groups; GitHub concurrency is not a project-wide distributed lock. Deployment operator must exclude legacy dispatches for the release window, inventory running workflows and preserve that constraint until completion. Do not claim serialization against uncooperative external CLI/legacy jobs. A future shared lock policy needs separate review.

Order: staged compatibility proof and quiescence → Firestore Rules only → all required Functions after dependencies resolved → QA smoke with separately authorized fixtures and cleanup. No Pages change required by this diff. Snapshot active ruleset/revisions/source generations before publishing. Rollback is not automatic: keep pending guards, drain operations and reconcile Auth/Firestore with version preconditions before selecting older code. Code rollback does not undo data/Auth changes. Never clear flags or delete identities to force recovery. See Sprint106 recovery runbook and predeploy audit.
