## WhatsApp Oficial V1 — Fase A: o que foi feito

Três commits atômicos, cada um verde em CI real antes do próximo:

1. `chore(functions): prepara runtime Node 22 para novos backends` +
   fix seguinte `fix(functions): corrige runtime declarado em
   firebase.json para node22` — `firebase.json` tinha
   `functions.runtime: "nodejs20"` hardcoded, que é o campo que o
   Firebase CLI realmente usa pro deploy; o bump de `engines.node` no
   `package.json` sozinho não teria efeito real. Sem redeploy de nada
   existente.
2. `feat(whatsapp): adiciona webhook e envio oficial seguro` — todo o
   backend (`functions/src/whatsapp/`), 7 Cloud Functions, coleções
   novas + Rules, scripts de piloto assistido, testes puros/Functions/
   Rules — ver `docs/WHATSAPP_OFICIAL.md` para o detalhe completo.
3. `feat(atendimento): integra WhatsApp oficial à inbox` — view de
   conexão nova + extensões pontuais na Central de Atendimento. Um bug
   real de CSS foi encontrado pelo CI real e corrigido num commit
   seguinte (`fix(atendimento): esconde de verdade o compositor fora
   da janela do WhatsApp`) — ver seção "Bug real encontrado e
   corrigido" em `docs/WHATSAPP_OFICIAL.md`.

**Playwright não pôde ser executado localmente nesta sessão**: o proxy de
rede deste ambiente de desenvolvimento bloqueia `gstatic.com` (`curl`
confirmou `403` na tunelagem CONNECT), e `firebase-init.js` carrega o SDK
do Firebase direto desse CDN — todo login real trava em `page.goto(...,
{waitUntil:"load"})`. Confirmado que **não é específico deste módulo**:
o mesmo teste-controle rodando `auditoria.flow.mjs` (já comprovado verde
em CI antes) falha exatamente do mesmo jeito neste sandbox. A validação
real de UI aconteceu só via CI (rede completa) — foi lá que o bug de CSS
acima foi encontrado e confirmado corrigido.
