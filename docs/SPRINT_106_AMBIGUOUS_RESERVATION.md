# Reservation RPC outcome and identity preservation

The creation syncId is generated before calling Firestore, then passed to capacity. A rejected await is not proof that a reservation did not commit. Unexpected reservation failures now preserve the initially disabled Auth identity and log UID/syncId for audited reconciliation; no reservation or flag is cleared automatically. A definitively rejected business operation (HttpsError before writes) can still remove only the freshly created, never-enabled identity. The limit remains transactionally enforced.

This is fail-closed preservation, not automatic recovery or success. If the reservation committed, its matching identity remains available and quota stays held pending reconciliation. If it did not commit, a disabled Auth-only identity can remain: future creation with the same email is rejected, and manual audited investigation is required. A quota decrease is not inferred from absence of an RPC response. Unknown Auth-create responses without a returned UID also require investigation, never lookup/delete by email.

The original failure was reproduced with a committed transaction followed by a lost response: old code deleted Auth and left a pending active document. Tests now require preservation. Emulator tests commit the actual reservation, inject a failure at the external return boundary, use deterministic Auth fakes, and verify lock/quota/identity, retries and definitive rejection. They do not induce real production network loss.

Runbook: prove no request is in flight; identify project/UID/tenant/syncId/version from logs; read Auth and Firestore independently. If both exist and match, reconcile with separate authorization and version preconditions. Auth present/document absent is NOT authorization to recreate a record or delete identity; investigate the original outcome, quota and intent and approve a case-specific action. Existing Auth-absent/document-present orphan states from older code require a dedicated intervention plan, not the normal sync completion planner. Never clear a flag, recreate/delete an identity or free quota automatically. Code rollback is not data rollback. Deploy remains NO-GO for the already documented WhatsApp/Storage/mixed-revision dependencies.
