# Reservation RPC outcome and identity preservation

The creation syncId is generated before calling Firestore, then passed to capacity. A rejected await is not proof that a reservation did not commit. A final HttpsError is not proof either: an earlier SDK callback attempt may already have committed. Uncertain reservation failures preserve the initially disabled Auth identity and log UID/syncId for audited reconciliation; no reservation or flag is cleared automatically. The limit remains transactionally enforced.

Capacity accumulates write-attempt evidence across the entire runTransaction call. It marks a write as possible BEFORE queuing tx.create, never resets that flag on retry, and records whether any callback observed an existing employee document. Only a business rejection with no writes attempted in ANY callback and no existing document observed can carry definitive-rejection evidence. The evidence is internal (WeakMap), bound to the original error plus ownerUid, employeeUid and syncId, and is checked by the handler before deleting only the freshly created, never-enabled Auth account. Matching only a class, code, message or client payload cannot provide this evidence. Unexpected transport errors remain uncertain even if no callback write was observed.

Conservative idempotency: encountering a reservation (same or different syncId/tenant) is NOT resumed as a successful create. Even the same operation returns an error and requires audited reconciliation; it must not enable Auth, overwrite a record, clear pending or free capacity automatically. A queued but ultimately uncommitted attempt can also leave a disabled Auth-only identity if a later attempt rejects: preserving it is intentional until the outcome is investigated. No cross-service transaction is claimed.

This is fail-closed preservation, not automatic recovery or success. If the reservation committed, its matching identity remains available and quota stays held pending reconciliation. If it did not commit, a disabled Auth-only identity can remain: future creation with the same email is rejected, and manual audited investigation is required. A quota decrease is not inferred from absence of an RPC response. Unknown Auth-create responses without a returned UID also require investigation, never lookup/delete by email.

The original failure was reproduced with a committed transaction followed by a lost response: old code deleted Auth and left a pending active document. The regression now also commits through the real SDK transaction, injects UNAVAILABLE at tx.commit return, lets the real SDK retry the callback and encounter the committed document, then requires identity/lock/quota preservation. It failed before this fix and passes after it. Additional Emulator tests cover a later owner rejection, changed syncId, another tenant/operation, wrapped HttpsError, normal creation and double-click. Auth is deterministic fake; neither these tests nor injected network errors prove real production Auth transport behavior.

Runbook: prove no request is in flight; identify project/UID/tenant/syncId/version from logs; read Auth and Firestore independently. If both exist and match, reconcile with separate authorization and version preconditions. Auth present/document absent is NOT authorization to recreate a record or delete identity; investigate the original outcome, quota and intent and approve a case-specific action. Existing Auth-absent/document-present orphan states from older code require a dedicated intervention plan, not the normal sync completion planner. Never clear a flag, recreate/delete an identity or free quota automatically. Code rollback is not data rollback. Deploy remains NO-GO for the already documented WhatsApp/Storage/mixed-revision dependencies.
